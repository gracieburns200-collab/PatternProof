# PatternProof Security Audit
**Scope:** `patternproofapp` (Lovable project `f496a23a-1a8f-408f-b5e0-e96d5947d49c`), live at patternproofapp.lovable.app, published & public. Full source (React/TanStack Start + Supabase), all 32 migrations, all server functions read directly.
**Threat model:** (1) abuser with physical/unattended access to survivor's device, (2) subpoena/discovery/law-enforcement requests, (3) cross-tenant leakage between attorney/survivor accounts, (4) curious/malicious authenticated attorney account acting outside their assigned clients.
**Method:** Full read of `supabase/migrations/*.sql` (32 files, every RLS policy), every `.functions.ts` server-side authorization path, auth/session code, PIN-lock and quick-exit implementation, env files, Clio integration, git-tracked secrets. Not a black-box pentest — no live exploitation attempted, no runtime access to the deployed Supabase project (only source).

Attorney access to this data is *not* via RLS (no attorney-read policy exists on these tables) — it's server-function-only via the service-role key, with authorization re-checked on every call (`assertLink`/`assertCaseAccess`/`assertOwnerLink`, ~15 call sites, all consistent). **Overall: workmanlike, above-average security engineering for the sensitive-data parts (messaging, attorney access, RLS) — the team clearly iterated on IDOR fixes repeatedly. The weak spots cluster in exactly the areas this specific audit was scoped to check: the physical-device-access safety features and the "can I delete this" question.**

## Findings, ranked by relevance to the stated threat model

### 1. HIGH — Auto-lock is advertised but not implemented
`settings.tsx` presents a UI control: *"Auto-lock timing — How many seconds of stillness before we lock the app back up,"* backed by `settings.sessionTimeoutSec` (default 60s, adjustable 15–1800s). **No code anywhere calls `lock()` after that timeout.** I read `pin-lock.tsx` in full (defines `lock()`) and `AppShell.tsx` in full (the only place with app-wide effects) — there is no idle timer, no `visibilitychange`/inactivity listener wired to it. The setting is stored and displayed as if it works, but does nothing. Practical effect: once unlocked, the app stays unlocked for the rest of the browser session (until the tab/browser closes), no matter how long it sits idle on a shared or unattended device. This is the single most safety-relevant bug found, because it's a documented safety feature a survivor could reasonably rely on.
**Fix:** wire an idle timer (e.g. `useEffect` in `AppShell.tsx` listening to `mousemove`/`keydown`/`touchstart`, resetting a `setTimeout(lock, settings.sessionTimeoutSec * 1000)`).

### 2. HIGH — Quick-exit doesn't clear browser back-button history
`QuickExitButton.tsx` / `AppShell.tsx` both do `window.history.replaceState(null, "", "/")` then `window.location.replace(exitUrl)`. `replaceState` only overwrites the *current* history entry — every prior in-app route the survivor visited (an incident detail page, the evidence list) is still one "back" press away after the panic exit. This is a known, well-documented failure mode for panic-button implementations (this is exactly what NNEDV's Safety Net guidance warns about). Given the app's own UX explicitly trains users to hit Esc-Esc or the exit button under duress, a same-tab back-button trap defeats the feature at the worst possible moment.
**Fix:** on quick-exit, either open the disguise URL in the same tab via full navigation *and* push several dummy history entries beforehand, or navigate via `window.location.href` to an entirely different origin combined with clearing/overwriting more of the history stack (there's no fully robust client-side fix for this — the standard mitigation is to push a stack of decoy entries during normal use so "back" from the disguise page doesn't reach app content).

### 3. HIGH — PIN is 4 digits, unsalted-per-install, stored client-side
`pin-lock.tsx`: `hash(pin) = SHA256("pp::" + pin)`. The `"pp::"` prefix is a constant across every install, not a per-user random salt — so the entire 10,000-value keyspace can be precomputed once and reused against any PatternProof user's `localStorage`. The PIN hash itself lives in `localStorage` (not sessionStorage), so it persists indefinitely and is trivially readable by anyone who opens devtools on the device (or via any XSS, though none was found). The 5-attempt/30-minute lockout is a real mitigation *for the on-screen PIN pad*, but does nothing against someone who copies the hash and cracks it offline in under a second.
**Fix:** derive the salt per-install (e.g. a random value generated once and stored alongside the hash, or better, use `crypto.subtle` with `PBKDF2`/many iterations), and treat the PIN as a low-assurance concealment layer rather than a cryptographic boundary — the biometric (WebAuthn) path is properly implemented and should be the recommended default where supported.

### 4. HIGH — Legacy token-only attorney sharing link (`/attorney/:token`) is live in production
`attorney-public.functions.ts` (`fetchSharedBundle`) + `src/routes/attorney.$token.tsx` implement a fully unauthenticated sharing mechanism: whoever holds the URL gets full incident narratives, evidence (with 1-hour signed URLs), case overview, and escalation flags — no login, no email verification, nothing beyond the bearer token. The token itself is strong (24 random bytes / 192 bits — not brute-forceable), so this isn't a guessing attack. The risk is entirely about **how the link gets shared**: if it's emailed and the survivor's email is on a monitored/shared device, or the link sits in browser history, "Sent" folder, or a printed page, anyone who obtains it has full read access with zero additional identity check — a materially weaker bar than the newer `attorney_client_links` invite flow, which requires the accepting party's authenticated account email to match the invitation. The page footer claims *"Access is logged"* — I found `last_accessed_at` is updated, but no entry is written to `audit_log` and no notification is sent to the survivor when their link is opened, so in practice nothing is "logged" anywhere the survivor would see it.
**Fix:** either retire this flow in favor of the authenticated invite system, or at minimum (a) notify the survivor (in-app + audit_log entry) every time the link is accessed, (b) default to a short expiry, (c) make the "Access is logged" claim true before keeping it in the UI copy.

### 5. MEDIUM — `time_entries` RLS allows cross-case billing injection
`"time_entries author full access"` (`FOR ALL USING (attorney_user_id = auth.uid()) WITH CHECK (attorney_user_id = auth.uid())`) never validates that `case_link_id` belongs to a link the inserting attorney actually has. Any authenticated attorney who learns another case's `link_id` (a UUID — not guessable, but also not something RLS should be trusting to stay secret) can INSERT a time entry against it. The app's own server function (`createTimeEntry`) does the right check before calling this — so the official UI is safe — but RLS is supposed to be the independent backstop against exactly this kind of direct-API bypass (the anon key is public by design; anyone with a valid attorney session can call PostgREST directly).
**Fix:** add `AND EXISTS (SELECT 1 FROM attorney_client_links l WHERE l.id = time_entries.case_link_id AND (l.attorney_user_id = auth.uid() OR EXISTS(...case_grants/case_collaborators...)))` to the `WITH CHECK`. Also add `AND status = 'active'` to `"time_entries case owner read"` — currently a *revoked* attorney can still read all time entries on a case they used to have access to.

### 6. MEDIUM — Audit log's "tamper-evident" claim doesn't hold against the account owner
`audit.functions.ts` builds a real hash chain (`entryHash = SHA256(ts|action|actor|ref|prevHash)`) — the mechanism is sound. But `audit_log`'s RLS policy is `FOR ALL USING (auth.uid() = user_id) WITH CHECK (...)`, i.e. the account owner has UPDATE/DELETE on their own rows, not just INSERT/SELECT. Anyone who can act as that user (including via direct PostgREST calls, bypassing `logAudit` entirely) can edit or delete their own chain — which defeats the point of a hash chain as evidence, since the chain is supposed to make retroactive edits detectable, not merely inconvenient through one code path. Settings page copy calls this "a tamper-evident record... hash-chained to the one before it," which overstates what's actually enforced.
**Fix:** `REVOKE UPDATE, DELETE ON audit_log FROM authenticated` (grant `INSERT, SELECT` only), so only the service role can ever modify history. Note this is still a self-reported log (the same account that might want to falsify events can always just not log them, or log false ones) — recommend the attorney-facing copy describe it as "an activity history for your own reference" rather than forensic-grade evidence, unless UPDATE/DELETE gets locked down.

### 7. MEDIUM — No self-service account/data deletion
No "delete my account" or "erase everything" path exists anywhere in the reviewed code (checked `settings.tsx`, all `.functions.ts` files, no deletion server function found). Given the safety scenario explicitly named in this audit (a survivor needing to erase their trail on short notice — device seizure, forced device inspection, shared custody-exchange devices), this is a real product gap, not just a compliance one. `ON DELETE CASCADE` is correctly set on all the FKs to `auth.users`, so the data model supports it — there's just no user-facing trigger.
**Fix:** add a settings-page "Delete my account and all data" flow that calls `supabase.auth.admin.deleteUser()` (service-role only, needs a dedicated server function with strong re-auth/confirmation) or, short of full account deletion, a "wipe my case data" function that truncates the user's rows across all owned tables and storage folders while leaving the login intact.

### 8. LOW — Env files tracked despite `.gitignore`
`.env`, `.env.production` (and presumably `.env.development`) appear in the Lovable file listing at `HEAD` even though `.gitignore` excludes `.env*`. Contents found: Supabase URL + anon/publishable key (`.env`), and a **live** Stripe publishable key (`pk_live_...`, `.env.production`). Both value types are meant to ship to the browser (anon keys are RLS-protected by design; Stripe publishable keys are not secrets), so the direct exposure risk here is low. The finding is about the *mechanism*: the gitignore rule that's supposed to keep env files out of the tracked tree isn't doing that, which means if a real secret (service-role key, Stripe secret key, Clio client secret) were ever pasted into one of these files by mistake, it would also get committed and be visible to anyone with repo access — silently defeating the exact control `SECURITY.md`'s own checklist calls out ("No secrets or API keys committed to the repository").
**Fix:** confirm whether these are actually committed in git history (vs. Lovable's sandbox just always showing working-tree files) — `git log --all -- .env.production`. If committed, they don't need rotation (nothing secret in them), but should be removed from tracking (`git rm --cached`) and history should be checked for anything with a service-role or Stripe *secret* key ever having been added the same way.

### 9. MEDIUM — Login page claims "END-TO-END ENCRYPTED"; the architecture doesn't support that claim
`login.tsx` displays, in the UI itself: **"🔒 END-TO-END ENCRYPTED"**. End-to-end encryption has a specific technical meaning — only the client holds the keys, and no one operating the server (not the app, not Supabase, not Lovable's infra) can read the plaintext. That is not what's implemented: incidents, evidence, communications, and voice-note transcripts are stored as ordinary rows/blobs in Supabase, readable in plaintext by the app's own service-role backend (which is how the entire attorney-portal feature works — server functions read survivor data directly), and by anyone with production database or storage access. This is normal, reasonable architecture for this kind of app (TLS in transit + access-controlled storage at rest is a legitimate security posture) — but it is not end-to-end encryption, and stating so on the sign-in screen is a claim a technically literate opposing party, journalist, or plaintiff's attorney could disprove by reading the source, which is a genuine liability exposure for a product whose credibility depends on precise, defensible security claims.
**Fix:** remove the claim or replace it with an accurate one ("Encrypted in transit and at rest," or "Private — only you and attorneys you explicitly share with can see your records").

### 10. LOW — `has_attorney_access` and related functions grant EXECUTE to `anon`
Migration `20260618040336` grants `EXECUTE` on `has_attorney_access`, `has_role`, `has_active_subscription` to `authenticated, anon, service_role`. A later migration (`20260623213804`) moves the canonical versions into a `private` schema with `REVOKE ALL FROM PUBLIC` and only grants to `authenticated, service_role` (correctly dropping the anon grant) — so this was already fixed. Noting only because the earlier public-schema copies were dropped in the same migration, which is good; no residual exposure found, but worth confirming in the live database that the `public.has_attorney_access` etc. functions are actually gone (`DROP FUNCTION IF EXISTS` was used, which is a no-op if already absent — can't confirm from source alone that the drop actually ran against production).
